# 写作风格规范（资深 HR 视角）

本文件是 `resume-builder` skill 的写作铁律，凡是出现"写一条 bullet""改一段经历"的环节，必须按此处规定执行。规则按"必须遵守 → 强烈推荐 → 黑名单"排列。

---

## 一、必须遵守（违反 = 直接驳回重写）

### 1. 每条 bullet 必须以"能力标签"加粗起手

格式：`<b>能力标签：</b>正文叙述。`

- 能力标签是 4–8 字的**抽象能力名**，不是动作名也不是任务名。
- 正文是该能力的具体证据（项目、动作、量化结果）。

| 反例（任务式） | 正例（能力式） |
| --- | --- |
| `负责飞书文档整理：把 PRD 沉淀成可读文档...` | `产品 0→1 规划与交付：从行业格局、用户画像与竞品图谱出发...` |
| `做了 GTM 文档：写了一份白皮书...` | `组织赋能与方法论沉淀：制定 GTM 策略、产品白皮书...` |
| `参加了百度黑客松：拿了奖...` | `赛事验证：拥有多次国内头部大厂首届 AI 黑客松参赛经历与获奖经验...` |

### 2. 抽象任务为能力，而不是相反

HR 看的是 "你能干什么"，不是 "你做了什么"。每写一句话先问自己：**这句话证明了哪种能力？** 找不到能力对应，这句话就该删。

### 3. 数字优先

凡能量化的全量化：

- 团队规模：`由 C9 博士与大厂高管组成的跨界团队`
- 竞品广度：`覆盖 20+ 主流玩家`
- 赛事数量：`多次入围` → 改成 `4 场首届大厂黑客松`（如果用户说还有更多就补"等"）
- 业务节奏：`双轨变现模型`、`多档套餐方案`

不能精确量化时，用"多次/多档/多份"等模糊量化，仍优于"一些/部分"。

### 4. 单页 A4 是品牌资产

任何编辑后必须重新渲染并目视确认仍是单页。如果溢出，按 `SKILL.md` 第 5 阶段的优先级裁剪。

### 5. 按证据强度分配篇幅

不要平均介绍所有项目，也不要为了单页把所有经历压成一条长句：

- 与目标岗位最相关、证据最完整的主项目保留 3–4 条。
- 能证明差异化能力的项目保留 2 条，通常分别写问题定义与方案/结果。
- 辅助经历保留 1 条或合并到工作经历、荣誉中。
- 优先删除重复信息，再缩短正文；不要牺牲关键项目的可读性。

### 6. 用工作经历解释履历连续性

当全职经历存在明显时间间隔时，将持续的创业、自由职业或独立产品探索作为正式工作经历呈现，而不是只藏在项目区：

- 使用用户能够确认的起止时间，不为填空虚构月份。
- 用市场验证、场景立项、客户调研、产品交付和外部验证证明这是一段连续实践。
- 具体项目在核心项目区展开；工作经历只保留时间线和能力总括，避免重复。

### 7. FDE 型能力必须有完整证据链

只有经历同时覆盖“客户现场 Discovery → 真实工作流拆解 → 产品/技术范围定义 → 原型或方案验证 → 一线反馈迭代”时，才可写“FDE 型产品实践”。

- 可以描述“FDE 型能力/实践”，但不得把产品经理经历改写成担任过 FDE。
- 未经证实的生产部署、工程所有权、规模化采用或业务结果不得补写。
- 非 Harness、部署或企业 AI 岗位，优先写“客户现场问题定义”，避免堆热词。

## 二、强烈推荐（保持文案统一感）

### 8. 动词起手清单

每条 bullet 正文的第一个动词决定调性。**优先**：

> 主导、牵头、独立完成、搭建、沉淀、构建、整合、驱动、验证、闭环

**避免**（被动 / 弱动词）：

> 参与、协助、了解、学习、负责一部分、有所贡献、跟随团队

### 9. "等"字策略

列举 3–4 个最强项后用"等"收尾，给 HR 暗示"还有更多"，又不显得清单化：

```
✅ 包括百度秒哒（最佳商业应用奖）、观猹（游戏赛道第四名）、小红书巅峰赛、好未来等
❌ 包括 A、B、C、D、E、F、G（穷举显得在凑数）
❌ 包括 A、B（少于 3 项时用"等"显得心虚）
```

### 10. 排序原则

| 维度 | 规则 |
| --- | --- |
| 项目经历整体 | 时间倒序，最新最上 |
| 同一条 bullet 内的列举 | 按含金量排序：先获奖、后入围；先头部公司、后中长尾 |
| 工作经历 | 时间倒序 + 体量优先：当前最相关公司放最上 |
| 核心优势 | 综合素质 → 核心技能 → 赛事验证（先讲底色，后讲外部背书） |

### 11. ATS 关键词喂底部

简历底部"技能与荣誉 → 核心技能"行是关键词串，不是叙述。直接堆放高频岗位词：

```
✅ 精通国内外主流 AIGC 模型、Vibe coding 敏捷开发、AI coding 工具链（Cursor、Claude Code、Windsurf）、Prompt Engineering。
```

每年根据岗位词风向更新这一行。当前（2025–2026）高频词：
**Cursor / Claude Code / Windsurf / Vibe coding / Prompt Engineering / Multi-agent / RAG / MCP / 多模态**

### 12. 称谓统一

一份简历内同一概念**只用一个词**：

| 推荐统一 | 不要混用 |
| --- | --- |
| 产品负责人 | 也叫"产品 Owner"、"PM lead" |
| 0→1 | 也叫"从零搭建"、"从 0 到 1" |
| 闭环 | 也叫"全链路"、"端到端"（两者只选一个） |

### 13. 上下游一致性

新增一段经历时，必须扫一遍**核心优势**和**技能与荣誉**两块，看是否要同步更新（例如新增了一个奖，核心优势"赛事验证"那条要把它带上）。

## 三、黑名单（看到立刻替换）

### 14. 冷僻 / 文绉绉的词

| 黑名单 | 替换为 |
| --- | --- |
| 熟稔、熟谙、深谙 | 精通、深度使用 |
| 精湛、卓越 | （直接删，让事实说话） |
| 颇具、略有 | （直接删） |
| 紧锣密鼓、不遗余力 | （直接删，套话） |

### 15. 微观技术细节

| 黑名单 | 解释 |
| --- | --- |
| `v1.0` `V2.3` | 简历层面不需要版本号，HR 不关心 |
| `13 周完成` `用了 3 个月` | 时长由公司任职区间体现，正文不重复 |
| 框架名（React、Express） | 写在底部技能行，不在项目正文堆砌 |
| 文件名 / 接口名 | 全部上抽象一层 |

### 16. 自我评价词

简历不是自传，删掉所有"我认为/我相信/我热爱"。直接陈述事实+成果。

### 17. 应用 vs 模型

正确措辞：

- **AIGC 模型**：Seedream、Kling、Pixverse、Veo、Sora2、可灵、即梦
- **AI coding 工具**：Cursor、Claude Code、Windsurf
- **AI coding 范式**：Vibe coding

不要写 "AIGC 应用" 来指代 Seedream/Veo/Sora2 这些底层模型。

### 18. 模型/产品名首字母大写

- ✅ Seedream / Kling / Pixverse / Veo / Sora2 / Cursor / Claude Code / Windsurf
- ❌ seedream / kling / cursor / windsurf

错拼一个工具名，HR 默认你"没真用过"。

## 四、写作 checklist（每次提交前过一遍）

```
- [ ] 每条 bullet 都以加粗能力标签起手
- [ ] 没有出现黑名单词汇（熟稔/精湛/v1.0/13 周/我认为）
- [ ] 模型名 ≠ 应用名，工具品牌名拼写正确且首字母大写
- [ ] 项目经历按时间倒序
- [ ] 同一条 bullet 内的列举按含金量排序
- [ ] 没有同一战绩在三个 section 重复出现
- [ ] 数字能量化的都量化了
- [ ] 履历时间线连续，未虚构空档月份或结果
- [ ] “FDE 型”措辞具备现场、定义、验证和反馈证据链
- [ ] 技能标签均保持单行
- [ ] 渲染后仍为单页 A4
```
