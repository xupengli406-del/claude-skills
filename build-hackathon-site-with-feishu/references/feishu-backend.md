# 飞书运营后台与报名集成

## 推荐数据层

### 报名原始表

原始数据只追加/更新，不手工删行。建议字段：

- 系统：活动 ID、报名时间、更新时间、报名编号、来源、UTM、同步状态、同意版本。
- 联系：姓名、邮箱、手机、微信、城市、公司/学校、身份、行业、职位。
- 能力：角色、项目经验、项目名、项目链接、贡献、AI 工具、作品集。
- 赛事：赛道、赛道理由、问题痛点、Agent 解法、参赛方式、队名、成员与分工、投入承诺。
- 运营：硬门槛、审核人 A/B、各维度分数、筛选结论、拒绝原因、联系状态、到场确认、门禁/餐饮/座位。

### 派生视图

- 待初筛、待复核、边界案例、入围待联系、已确认、候补、未通过。
- 队伍视图、门禁视图、餐饮视图、胸牌/队牌视图。
- 同步失败、重复报名、字段缺失、撤回/删除请求。

## 服务端双写

### 写入顺序

1. 验证请求来源、速率和字段。
2. 规范化邮箱/手机号，生成幂等键。
3. 本地数据库 upsert。
4. 创建同步任务。
5. 服务端调用飞书 API append 或 update。
6. 保存飞书行范围、时间、结果和错误。

### 为什么保留本地数据库

- 飞书 API 短暂不可用时不丢报名。
- 可做幂等、重试、审计和撤回。
- 站点可以向用户返回已接收状态，同时准确显示同步状态。

### 重试策略

- 网络/429/5xx：指数退避，最多 5 次，增加随机抖动。
- 401/99991663 等权限错误：停止自动重试，报警并检查应用权限/授权。
- 表头变化/范围错误：停止写入，标记 schema mismatch。
- 提供受保护的重试入口或后台任务；不要让用户重复提交造成多行。

## 飞书应用配置

1. 创建企业自建应用。
2. 开通电子表格读写所需权限并发布版本。
3. 将目标表格授权给应用或确保应用可访问。
4. 记录 Spreadsheet Token 与 Sheet ID；不要把 App Secret 写入代码。
5. 托管环境变量：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_SPREADSHEET_TOKEN`、`FEISHU_SHEET_ID`。
6. 用 tenant access token 从服务端调用 Sheets API。

## 权限模型

- 官网只调用自己的 `/api/register`，绝不暴露飞书凭证。
- 报名原始表仅组委会核心人员可见。
- 门禁、餐饮、评委等只获得完成工作所需字段。
- 公开获奖文档只包含项目/队伍公开信息。
- 定义数据保留期限、撤回入口和访问日志。

## 表头契约

- 代码字段映射与飞书表头必须一一对应；上线前读 A1:Z2 验证。
- 表头有版本号，如 `registration-schema-v1`。
- 修改表头先改映射和测试，再发布；不要直接插列破坏位置映射。
- 更稳健的实现可先读取表头生成列号映射，而不是硬编码 A:L。

## 报名成功语义

- `201 synced=true`：本地保存且飞书已同步。
- `202 synced=false`：本地保存，飞书排队重试；前端应告诉用户“已收到”，不要要求重复提交。
- `400`：字段无效。
- `409`：业务规则不允许重复且无法更新。
- `429`：提交过快。
- `500`：本地保存失败。

## 防护

- 服务端字段限长、枚举、邮件/URL校验，转义公式注入：以 `= + - @` 开头的自由文本写入表格前加安全前缀。
- 限流、蜜罐字段、可选验证码、请求体大小限制。
- 日志不打印完整个人信息或 App Secret。
- 隐私同意必须带版本和时间；营销授权与赛事联络分开勾选。
- 处理删除请求时同步清理本地和飞书，保留最小审计记录。

## 端到端验收

1. 读取表格信息，确认 token、sheet id、表头。
2. 提交一条带明显 `TEST-` 标记的虚构报名。
3. 回读飞书，确认每列映射、时间、来源、报名编号。
4. 用相同邮箱修改字段，确认更新同一行。
5. 临时使用错误 sheet id 验证失败记录和重试，不在生产环境执行破坏性测试。
6. 清理测试记录或标记为测试。
