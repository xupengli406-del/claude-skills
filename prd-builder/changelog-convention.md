# 变更日志与红字增量标注规则

PRD 是活文档。版本管理与红字标注是这套 PRD 风格的关键识别符。

---

## 一、版本号规则

```
v{大版本}.{小版本}
```

| 触发条件 | 版本号变化 | 例子 |
| --- | --- | --- |
| 架构级重构 | 大版本 +1 | 单轨计费 → 双轨计费：v1.x → v2.0 |
| 模块新增 / UI 重构 / 规则调整 | 小版本 +1 | 新增 Token 充值弹窗：v1.2 → v1.3 |
| 文字勘误 / 截图替换 | 不升版本，直接覆盖 | — |

---

## 二、变更日志表格规则

> **每个小版本一张独立 `<lark-table>`**，不要把多版本塞在一张表里 —— 飞书会因为内容多寡导致行宽错乱。

每张表的固定参数：

```html
<lark-table rows="1" cols="4" column-widths="109,117,116,399">
```

四列：

| 列 | 内容 | 写法 |
| --- | --- | --- |
| 1 | 时间 | `YYYY-MM-DD`，红字 |
| 2 | 版本号 | `v{大}.{小}`，红字 |
| 3 | 变更人 | 中文姓名，红字 |
| 4 | 主要变更内容 | 编号列表 + 每条用红字 |

新增/重要变更整段包红：

```html
<lark-tr>
  <lark-td><text color="red">2026-04-17</text></lark-td>
  <lark-td><text color="red">v1.3</text></lark-td>
  <lark-td><text color="red">李旭鹏</text></lark-td>
  <lark-td>
    1. <text color="red">计费体系重构为 V3.0（订阅+Token充值双轨制、预扣/实扣/释放机制、三种Token来源及过期策略）；</text>
    1. <text color="red">新增「六（附）系统架构与核心数据流转」章节…</text>
  </lark-td>
</lark-tr>
```

> 注意：`1.` 编号在 markdown 里全部写 `1.` 也能正常渲染为递增编号，飞书识别一致。

---

## 三、变更内容写法规范

每条变更必须含 **3 要素**：

1. **动作**（新增 / 重构 / 调整 / 删除）
2. **对象**（章节名 / 模块名 / 功能点编号）
3. **关键决策点**（用括号标在对象后）

正例：

```
新增「六（附）系统架构与核心数据流转」章节（5 节点架构图、4 条核心流程图、计量推送说明、各方职责矩阵）
```

反例：

```
❌ 优化了系统架构（缺对象 + 缺决策点）
❌ 重构 6.7（缺动作描述 + 缺章节名）
❌ 改了一些小问题（三要素全缺）
```

每条不超过 80 个汉字；超过就拆两条。

## 四、正文红字标注规则

红字 `<text color="red">…</text>` 的语义是 **"本次小版本新增 / 修改"**。

### 红字标注范围

| 范围 | 是否红字 |
| --- | --- |
| 新增的章节标题 | ✅ 红字 |
| 新增的功能点（整个 X.Y 块） | ✅ 标题 + 关键句红字（不要全文红字） |
| 修改的规则条目 | ✅ 仅修改的那行红字 |
| 修改的尺寸/数字 | ✅ 仅数字红字 |
| 删除的内容 | ❌ 直接删，不标 |
| 已稳定一个版本以上的红字 | ❌ 退红（在下个小版本时一并清理） |

### 红字"退红"节奏

每升一个**大版本**（v1 → v2 / v2 → v3）时，统一清理上一个大版本周期里所有 `<text color="red">` 包裹（保留内容，去掉标签），让文档回到"全黑"基线，然后这个大版本周期内的小版本变更再用红字累加。

---

## 五、章节标题红字示例

```markdown
# <text color="red">六（附）、系统架构与核心数据流转（新增）</text>
```

注意：

- 红字范围必须把整个标题（含编号 + 标题 + 后缀「（新增）」）全包。
- 后缀写 `（新增）` 而非 `(NEW)`，保持中文一致性。

---

## 六、增量更新工作流

当用户说"在 v1.3 基础上做 v1.4"时：

```
- [ ] 1. 读旧版 PRD，找出本次要新增/修改的章节范围
- [ ] 2. 把上一个版本的红字（v1.3 标记）保留，不动
- [ ] 3. 新增/修改部分用 v1.4 的红字标注（同一份 PRD 红字会"叠加"）
- [ ] 4. 在「二、变更日志」追加一张新 lark-table（v1.4 行）
- [ ] 5. 顶部「一、版本信息」的版本号 callout 更新为 v1.4
- [ ] 6. 在 PRD 的对应章节标题或正文里把"待补/待评审"红字尽量收掉
```

> 不要"覆盖式"重写整个 PRD —— 旧版本的红字是历史 traceability，研发会按红字对照变更范围。

## 七、版本变更日志的"用户故事"写法

变更日志不是 git log，是给评审/利益相关方看的"产品决策摘要"。

| ❌ 像 git log | ✅ 像产品决策摘要 |
| --- | --- |
| 修改了 LoginModal.tsx 的样式 | 账户系统登录弹窗重构（B端企业登录/C端个人登录双模式、企业登录入口、UI 尺寸优化） |
| 加了个 useToken hook | Token 余额体系（含三种 Token 来源 + 过期策略） |
| 修了一些 bug | （删除：bug 修复不写进 PRD 变更日志） |

---

## 八、变更日志 checklist

每次小版本提交前过一遍：

- [ ] 新加了一张独立 `<lark-table>`，不是在旧表里追加行
- [ ] 时间 / 版本号 / 变更人三列均为 `<text color="red">`
- [ ] 主要变更内容每条都满足"动作 + 对象 + 决策点"三要素
- [ ] 顶部「一、版本信息」的版本号 callout 已同步更新
- [ ] PRD 正文里对应的章节 / 功能点也已加红字
- [ ] 上个大版本周期的稳定红字已退红（仅在大版本升级时执行）
