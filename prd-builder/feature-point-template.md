# 功能点写作规范

每个 `### 功能点 X.Y` 必须遵循此规范。功能点是 PRD 的最小可复用单元，写法不一致会让研发反复回头追问。

---

## 标准结构（拷贝直接用）

````markdown
### 功能点 X.Y：功能点中文名（可选副标题）
<grid cols="2">
  <column width="40">
    **页面/交互**
    - 触发方式：…
    - 形态/尺寸：…
    - 视图清单（如有多视图，分小标题）：

    **{子视图名 1}**：
    - 元素 a（含尺寸/颜色/状态/默认值）
    - 元素 b
    - …

    **{子视图名 2}**：
    - …
  </column>
  <column width="60">
    **{子视图名 1}：**
    <image token="待补" width="2559" height="1398" align="center"/>

    **{子视图名 2}：**
    <image token="待补" width="2559" height="1398" align="center"/>
  </column>
</grid>

**规则**
- 业务规则 1
- 状态机规则 2
- 边界 / 异常规则 3
- Mock 标记或第三方对接说明

---
````

---

## 必填项 checklist

每个功能点交付前都要满足：

- [ ] **触发方式**：点击什么 / URL 进入 / 由什么状态触发，明确到具体按钮或路由。
- [ ] **形态/尺寸**：弹窗最大宽 px、卡片圆角 px、按钮高 px、字号 pt、关键色 #hex。
- [ ] **元素清单**：每个交互元素都列名 + 关键属性（占位文字、默认值、是否禁用条件）。
- [ ] **多视图分组**：超过一个视图（如登录/注册/企业登录）必须分小标题分别列。
- [ ] **截图占位**：右列至少一张 `<image token="待补" align="center"/>`。
- [ ] **规则区**：至少 3 条 — 业务规则、状态机/校验、异常/兜底。
- [ ] **Demo 实现状态**：在「五、模块总览」表里同步标 `已完成` / `Mock` / `待实现`。
- [ ] **`---` 分隔符**：与下一个功能点之间必须有水平线。

---

## 规则区写作分类

`**规则**` 区不是流水账，按下面四类组织：

| 类别 | 例子 |
| --- | --- |
| **业务规则** | 当前为 Mock 实现，1.5 秒后模拟支付成功 |
| **状态/校验** | 协议未勾选时按钮 disabled / 所有输入框为受控组件 |
| **边界/异常** | 余额不足 → 弹出充值；生成失败 → 释放冻结 |
| **第三方对接** | 调用中台「预扣 Token API」/ 通过 Stripe 完成支付 |

每类至少 1 条，没有就标 `<text color="red">待评审</text>`，不要硬编。

## 格子比例选择

| 场景 | grid 比例 | 备注 |
| --- | --- | --- |
| 大多数功能点（左字 + 右图） | `cols="2" width="40"/"60"` | 默认 |
| UI 极简但规则多 | `cols="2" width="60"/"40"` | 字多图少时反过来 |
| 仅文字（如规则汇总、价格表） | 不用 grid，直接全宽 | 例如功能点 6.4 价格表 |
| 三图并排（如同一弹窗的三个 tab） | `cols="2"` 但右列堆三张 image | 不要做 cols="3"，飞书渲染会挤 |

## 价格表 / 计量表的特殊写法

不放进 grid，直接全宽 `<lark-table>`。模板：

```markdown
### 功能点 X.Y：模型按量计费价格表

<lark-table cols="5" header-row="true">
  <lark-tr>
    <lark-td>模型 ID</lark-td>
    <lark-td>类型</lark-td>
    <lark-td>计费单位</lark-td>
    <lark-td>单价（USD）</lark-td>
    <lark-td>说明</lark-td>
  </lark-tr>
  …
</lark-table>

**规则**
- 价格以 …
- 余额按 …
```

## 状态机的标准写法

涉及状态机的功能点（订阅/支付/生成），在规则区下面追加一个 ASCII 状态图：

```plaintext
┌─────────────┐  支付成功   ┌──────────┐  到期未续 ┌─────────┐
│ 未订阅      ├────────────▶│ 订阅中   ├──────────▶│ 7天宽限│
└─────────────┘             └──────────┘           └────┬────┘
                                                       │ 仍未续
                                                       ▼
                                                  ┌─────────┐
                                                  │ 已降级 │
                                                  └─────────┘
```

把状态机 ASCII 化的好处：研发可以照着画类型、设计可以照着画 UI。

## 子视图 vs 单独功能点的取舍

**判断准则**：是否共用同一个触发入口、是否共用同一份关闭按钮 / 弹窗壳。

- **同入口、同壳** → 同一个功能点的多个子视图（例：登录弹窗的 C端登录/C端注册/企业登录）
- **不同入口或不同壳** → 拆成两个功能点（例：登录弹窗 vs 用户菜单弹窗）

错拆会让研发认为是两个独立组件做重复工作；错合会让 UI 评审找不到分镜稿。

## 命名一致性

功能点编号：`X.Y` 主编号，小迭代用字母后缀 `X.Yb`（例：`3.4` 参考图，`3.4b` 高级生成参数）。

功能点标题中文不写"模块"二字（"模块"留给二级标题），直接用业务名：

```
✅ 功能点 1.1：登录弹窗（B端企业登录/C端个人登录）
✅ 功能点 6.7：Token 充值弹窗
❌ 功能点 1.1：账户系统-登录功能模块
```

---

## 最常见的 3 个错误

1. **只写 UI 不写规则** — UI 是 Figma 的事，规则才是 PRD 的命。
2. **Mock / 真实没区分** — 当前 Demo 是哪些写死的、哪些已对接，必须显式标。
3. **截图 token 缺位** — 即使图还没出，先放 `<image token="待补"/>` 占位，便于后续灌图。
